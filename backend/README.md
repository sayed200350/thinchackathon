# Browser workbench

With Python 3.10+ installed, double-click `backend/start-workbench.cmd` on Windows, or run from the repository root:

```powershell
python -m backend.workbench_server --open
```

Open **http://127.0.0.1:8767**. Keep the terminal open; Ctrl+C stops it. No additional packages or frontend build are needed. The claimant service can run alongside it on port 8765. `python -m backend --open` also opens the workbench.

The workbench starts **empty**: no claims are preloaded. Use **Upload CSV** to load your own file. It uses the fresh database `backend/.local/workbench.sqlite3` and does not open older databases. To preload claims anyway, pass `--claims FILE [FILE ...]`.

Open [Incoming claims](http://127.0.0.1:8767/incoming) to see submissions directly on the demo machine. The workbench authenticates to the claimant API with the server's `CLAIM_REVIEWER_KEY` from the environment or a private settings file. The default claimant API port is 8765. For the Thinc demo, run `python -m backend.workbench_server --open --intake-port 8766 --env-file /tmp/thinc-staff-handoff/runtime.env`. Anyone using the local workbench can view submitted claims and original documents. **Replay this claim** tests a proposed quote limit against the recorded evidence.

## Policy upload (Word or JSON)

Upload the policy like the CSV: **Upload policy** accepts the Word document (`.docx`) or the engine's JSON. Nothing is assessed until both a CSV and a policy are loaded. A Word policy is converted on the server (`engine/docx_policy.py`) and the page lists the rules it read so you can check them. The converter understands the supplied wording ("Send to human_review if …; or quote_eur is greater than €1,500." / "Otherwise, send to routine_processing.") and refuses anything else with a message rather than guessing. Only `and`-free conditions on the claim fields are supported. The supplied `policy_v1.docx` converts to exactly the bundled v1 policy. Candidate (v2) policies can be uploaded as Word or JSON the same way and are matched to the uploaded policy's `policy_id`.

## Use the platform

1. Select a claim. **Why this decision?** shows a short **Why**, **Next step**, and policy reference. Relevant amounts come from the uploaded policy and claim; missing information remains visible even when human review takes priority. **View policy checks** opens the supporting facts and full rule evaluation. Alternative outcomes and verified "what could change the outcome" examples are expandable. The employee copy (`decision.audit.detail.employee` and `concise_explanation`) also appears in CSV exports; full technical evidence remains in the audit. It is generated by `engine/explain.py` from the recorded evaluation, never from a second set of rules.
2. Expand **Edit structured facts** for a temporary test. Changes do not modify stored machine evidence.
3. Upload an authorized CSV in the supplied schema, or choose a clearly labelled hypothetical candidate policy. Click **Run assessment**.
4. Download the exact seven-column CSV, full JSON report or one-record-per-line **audit JSONL**. Invalid records are explicitly marked and retained in order.
5. On a saved open claim, enter a reviewer identity, different handling step and reason. Corrections persist across refresh/restart with version and UTC timestamp. Original machine decisions remain immutable.

Candidate comparisons reuse stored closed-case decisions when working with saved claims. Uploaded/edited fixtures without a trusted historical record are explicitly described as computed exercise v1 results. Original machine recommendations and effective reviewer overrides remain separate; CSV simulation exports machine outcomes.

Uploads and edits are session-local. The app never treats a candidate preview as an official release. Independent accuracy for synthetic/candidate cases is **not measured**.

## Policy-owner review

Policy-owner approval is disabled unless the server operator configures the `POLICY_TWIN_OWNER_TOKEN` environment variable with a private credential before starting the server. Do not commit that credential. Restart the server after configuring it.

Upload a genuinely supplied candidate JSON with a distinct `version` and a `source` attribution. In **Policy-owner review**, enter the owner name, credential and review reason. The server validates the policy, runs generated conformance checks, binds its immutable version/hash and appends a timestamped approval event including the original v1 hash. Hypothetical fixture versions cannot be approved. Approval records review only; deployment/activation is not automatic.

This local prototype uses a shared owner credential, not enterprise identity management. Only holders of that credential can submit approval. Claim-reviewer names remain entered demo identities. SQL triggers prevent updating/deleting original machine records, correction history, version bindings and approval events through normal database operations.

## API and checks

Existing claim list/detail/correction routes remain available. Machine decision objects now include additive audit fields and richer explanations.

| Endpoint | Purpose |
| --- | --- |
| `GET /` | Browser interface |
| `GET /api/workbench` | Saved synthetic claims and v1 policy |
| `POST /api/workbench/run` | Assess `claims` or `csv`, with optional `candidate`, `policy`, `use_saved` and returned `input_issues` |
| `POST /api/policies/approve` | Owner review: `policy`, `actor`, `reason`; credential in `X-Policy-Owner-Token` |

Candidates are `none`, `threshold`, `ev`, or `custom`. The two named examples are synthetic fixtures, never official v2. Successful batch responses include per-row errors as well as valid decisions; invalid policies return 400, version conflicts 409 and unauthorized owner reviews 403. Uploaded claim data is not persisted. Candidate configurations are registered immutably on preview. Batches support up to 2000 records / 2 MiB request bodies.

### Submitted-claim policy replay

In **Incoming claims**, open a receipt reference, then select **Compare recorded V1 with V2**. The server replays the saved evidence revision through the same engine used by the workbench. It checks the original decision and policy fingerprint before returning a preview. Closed claims retain the recorded decision. Reviewer corrections remain visible separately.

The V2 configuration in `engine/configs/policy_v2.json` was compiled from the supplied motor change notice (PDF SHA-256 `57a00c9c2dca66b61b7108740ab848ca13d822b3e77b9a98ad3c3ec98dbde7a6`). It lowers the quote limit to €1,200 and adds the high-voltage EV battery trigger. For a reproducible boundary demo, start the labelled sample claim in the chatbot and attach the sample incident report and `backend/fixtures/quotes/itemized-1300.pdf`.

A hosted insurer app should authenticate staff in its own server and call the fixed HTTPS staff gateway. Start that gateway with `--read-only` and a separate upstream reviewer credential for read-only hosting. Keep the upstream origin and key in server secrets. POST `/api/staff/policy-replay` with `reviewer_key`, `reference`, `expected_revision` and `target_version: "v2"`. A stale revision returns 409. The result includes the recorded and proposed version, route, matched rule, explanation, relevant amended rules, recheck flag and closed-claim retention. Opening an insurer-only link locally uses `/incoming#CLM-…`.

### Local judge demo

Start the existing garage-only gateway with its upstream set to `http://127.0.0.1:8782`. Use that gateway's phone-accessible HTTPS origin for `python -m backend.judge_demo --garage-public-origin <origin>`. Set the same random server-only `JUDGE_DEMO_KEY` (at least 32 characters) for that process and the insurer dev server. Set `JUDGE_DEMO_PORT=8782` for the insurer. Start the mobile preview with `python demo/chat-redesign/serve.py --port 8090 --backend http://127.0.0.1:8766 --judge-port 8782`.

Open `/judge/chat` in the mobile preview, use the sample incident report and €1,300 quote, then open **Submitted** in the insurer app and refresh the inbox. Scan the garage QR and upload the sample €1,800 quote to the same receipt. Each judge server starts with an empty, temporary SQLite database and accepts the bundled sample documents. Restarting it starts a new session. Normal claimant receipts still open at `/chat`.
